Complete Screen-by-Screen UI Specification 1. Executive Summary Velocyverse is a SaaS platform that automates security posture assessment of a customer's Microsoft 365 environment. A prospective or existing customer connects their M365 tenant (via a multi-tenant, admin-consented Azure AD app) and Velocyverse pulls configuration data across eight core M365 surfaces — Microsoft Entra ID, the M365 Admin Center, Microsoft Purview, Email/Exchange Online (incl. Defender for Office 365), Intune, Cloud Apps (Defender for Cloud Apps), Teams, and SharePoint — evaluates that data against a structured control catalog, and produces a scored, prioritized security assessment report. The product offers three assessment tiers of increasing depth and decreasing automation share: a free Trial Assessment (0% automated, a 10–12 question self-reported questionnaire that produces an estimated score), a Quick Assessment (100% automated, covers critical controls across all eight modules), and a Detailed Assessment (80% automated + 20% expert-reviewed manual assessment, intended for compliance-grade, audit-ready output). A Detailed Assessment routes the residual 20% to an internal Assessor via an Admin-managed assignment queue, closing the loop between automation and human judgment for controls that require business context (e.g., "is this exception justified?"). This PRD is written to hand off to an AI coding agent (Kilo AI) for scaffolding and iterative build, and covers the full platform: Client, Admin, and Assessor experiences, all three assessment tiers, the assessment/scoring engine, and the underlying Microsoft Graph integration — as confirmed for the first build. 2. Problem Statement &amp; Opportunity 2.1 The Problem Organizations running Microsoft 365 frequently have security misconfigurations they are unaware of — MFA not enforced tenant-wide, no Conditional Access policies, legacy authentication left enabled, DLP not configured, audit logging disabled, admin accounts not separated from day-to-day accounts, and so on. Discovering these gaps today typically requires either a manual audit by an internal IT/security team (time-consuming, requires specialist M365 security knowledge) or an expensive third-party security assessment engagement (consulting-led, slow turnaround, high cost, low repeatability). 2.2 The Opportunity Self-serve, automated first pass: most of what a manual M365 security audit checks can be pulled programmatically via Microsoft Graph and evaluated against a known-good control baseline (aligned to frameworks like CIS Microsoft 365 Foundations Benchmark, Microsoft Secure Score, and NIST/ISO mappings). Tiered depth matches buyer intent: a free/low-friction Trial builds trust and demonstrates value pre-purchase; a Quick Assessment gives a fast, cheap, fully-automated read; a Detailed Assessment adds expert review for organizations that need audit-ready, defensible output (e.g., for compliance, cyber-insurance, or board reporting). Recurring/repeatable revenue: because assessments are cheap to run once the platform exists, this supports both one-off paid assessments and a recurring "re-assess periodically" motion (referenced directly in the wireframes: "Take action &amp; Improve security... re-assess"). 2.3 Why Now Microsoft Graph and the Graph Security API expose the vast majority of configuration signals needed for this kind of assessment via well-documented, delegated-permission APIs, and Azure Marketplace provides a natural distribution channel directly to the ICP (any organization already running Microsoft 365 / Azure). 3. Personas &amp; Roles 4.1 Client / End User ("User") The primary buyer/operator persona — typically an IT Admin, MSP engineer, vCISO, or founder/ops lead at an SMB running Microsoft 365. Logs in with their own account (tenant-agnostic identity — this is a Velocyverse account, separate from the M365 tenant identity), then separately connects one or more client M365 tenants for assessment. Goals: quickly understand security posture, get actionable remediation guidance, produce a shareable report. Key actions: sign up/login, run Trial, connect tenant, run Quick/Detailed assessment, view results, download/share report, view assessment history, manage account. 4.2 Admin (Platform/Internal Admin) Internal Velocyverse staff who operate the Detailed Assessment pipeline and manage the Assessor workforce. Not a customer-facing role. Goals: keep the Detailed Assessment queue moving, ensure every request is assigned to a qualified Assessor, manage the Assessor roster. Key actions: view/manage active Detailed Assessment requests, assign requests to Assessors, manage Assessors (add/remove/edit), view released reports. 4.3 Assessor (Internal Subject-Matter Expert) Internal (or vetted contractor) M365 security specialist who performs the manual 20% of a Detailed Assessment: reviewing automated findings in context, gathering business requirements, requesting supporting documentation from the client, and recording expert judgment findings. Goals: efficiently work through assigned requests, get what they need from the client without excessive back-and-forth, produce defensible findings. Key actions: view assigned requests, view completed requests, collect additional data, request supporting documents from client, record findings that feed the Recommendation Engine. 4.4 Role Summary Table Role Access Surface Cannot Do Client / User Own org's dashboard, own tenant connections, own assessments, own reports See other orgs' data; assign Assessors; access Admin/Assessor portals Admin Admin portal: all Detailed requests, Assessor roster, released reports Directly edit a client's raw assessment data; impersonate a client without audit trail Assessor Assessor portal: only requests assigned to them See unassigned requests; manage other Assessors; access Admin functions 5. No Yes Yes Input method 12-question guided wizard Live Microsoft Graph pull, all 8 modules Live Microsoft Graph pull (8 modules) + Assessor review Coverage Key security areas only (high-level) Critical security controls across all modules All security controls across all modules, incl. exceptions/context Output Estimated score (0–100) + top recommendations Full scored report: overall + per-area scores, findings, recommendations Full scored, expert-reviewed, audit-ready report Turnaround Instant Minutes Up to a few business days (Assessor SLA) Price (from wireframes — confirm before build) Free $5 (example price shown in wireframe) $7 (example price shown in wireframe) Best for First-touch / lead generation Fast self-serve check, regular re-checks Compliance, audits, cyber-insurance, board reporting 6.2 Trial Assessment A 10–12 question guided wizard covering the highest-signal security controls (MFA enforcement, Defender for Office 365, admin account separation, Conditional Access, Intune device management, disk encryption, privileged access hygiene, password policy, audit logging, DLP, backup, security awareness training — as shown in the existing wireframe). Each question is Yes / No / Unsure. A weighted scoring formula converts answers into a 0–100 score with a qualitative band (Poor/Fair/Good/Excellent), matching the existing "25/100 – Poor" wireframe. No tenant connection or Graph permissions are required — this is entirely self-reported, and the report should be explicit that this is an estimate, not a verified assessment. The results page always ends with a strong CTA to connect the tenant for a verified assessment. 6.3 Quick Assessment Fully automated. Once a tenant is connected, Quick Assessment pulls a defined subset of "critical" controls (a curated high-signal subset of the full control catalog) across all 8 modules, runs them through the Assessment Engine and Scoring Engine, and produces the full Results Dashboard shown in the wireframe (overall score, per-module score for Entra/Email/Purview/Intune, top findings with severity, next steps, downloadable PDF/Excel report). Designed to complete in minutes with no human involvement. 6.4 Detailed Assessment Automated data collection runs across the full control catalog (not just the critical subset) for all 8 modules — this constitutes the "80% automated" portion. The remaining ~20% consists of controls that inherently require human judgment or business context and cannot be fully resolved from configuration data alone — for example: "Is this specific Conditional Access exception justified by a documented business reason?", "Does the DLP policy scope match the organization's actual sensitive-data footprint?", or controls where the automated check surfaces an ambiguous/needs-review state. These are routed into the Manual Assessment Workflow (Section 9), assigned by an Admin to an Assessor, who reviews context, requests supporting documents from the client if needed, and records findings that are merged back into the same assessment by the Scoring &amp; Recommendation Engine. Note: the exact 80/20 split is a target design ratio, not a hard rule enforced in code — the real mechanism is: every control in the catalog is tagged automatable: true/false (see Section 15 data model, ControlCatalog.automatable), and the ~20% figure is simply the expected proportion of controls tagged non-automatable across the full catalog. This should be validated once the control catalog is finalized. See Section 21 for exactly how each tier's classification (checklist / high-level automated / detailed automated+manual) determines the Microsoft Graph permission footprint requested, Section 22 for how tier availability is gated by subscription plan, and Section 24 for the incremental consent mechanism that avoids ever requesting all permissions in one blanket ask. 7. Functional Requirements 8.1 Authentication &amp; Account Management ID Requirement FR-1.1 Users can sign up with Full Name, Email, Password, Company Name, Company Size, and Phone Number (with country code). Email must be validated as a real, deliverable address; a warning note should discourage personal email addresses (per wireframe: "Kindly enter your tenant's mail id"). FR-1.2 Users can log in with Email/Password, Google OAuth, or Microsoft OAuth. FR-1.3 MFA is required at login for all roles (Client, Admin, Assessor). Support at minimum TOTP authenticator app; email/SMS OTP as a secondary option. FR-1.4 "Forgot password" and "Resend verification email" flows are supported. FR-1.5 Users can change Name, Email, Phone Number, and Password from account settings. FR-1.6 Users can delete their account (soft-delete with a grace/recovery period recommended; must cascade-handle or anonymize associated assessment data per retention policy). FR-1.7 Sessions expire after a configurable inactivity window; "Remember me" extends session lifetime per security policy. FR-1.8 Admin and Assessor accounts are provisioned by an Admin (not self-service sign-up) and use the same login/MFA mechanism, routed to role-specific dashboards post-login. 8.2 Onboarding ID Requirement FR-2.1 First-time users see a Tenant Onboarding Guide (product tour) after signup, explaining Trial vs. Tenant Connection paths. FR-2.2 The pre-connection User Dashboard presents exactly two clear entry points: "Start Trial Assessment" and "Connect Your Tenant", each with a short benefits list, matching the existing wireframe. FR-2.3 A downloadable step-by-step PDF/User Guide is available for the tenant connection process, plus in-app guided steps. 8.3 Trial Assessment ID Requirement FR-3.1 Present a fixed set of 10–12 Yes/No/Unsure questions covering the highest-signal control areas (see Section 6.2). FR-3.2 Compute a weighted score (0–100) and qualitative band (e.g., Poor &lt;40, Fair 40–69, Good 70–89, Excellent 90–100 — confirm exact thresholds with stakeholder before build). FR-3.3 Results page shows: overall score gauge, answer summary (counts of Yes/Unsure/No), per-question breakdown, Key Recommendations (derived from "No"/"Unsure" answers), and a persistent CTA to connect the tenant. FR-3.4 Results can be downloaded and the trial retaken. FR-3.5 Trial Assessment does not require a tenant connection and stores no M365 configuration data — only the questionnaire answers. 8.4 Tenant Connection ID Requirement FR-4.1 Tenant connection uses a multi-tenant Azure AD (Entra ID) app registration. The client's tenant Global Admin (or equivalent privileged role) completes the Microsoft admin-consent flow, granting the read-only Graph scopes listed in Section 16. FR-4.2 The system must clearly state, before consent, exactly what permissions are requested and that access is read-only. FR-4.3 If consent is denied or partially granted, the affected module(s) must be clearly flagged; the user can retry consent at any time from the dashboard. FR-4.4 A tenant can be reconnected/re-authorized if a token expires or is revoked; connection status is visible on the dashboard (Connected / Needs Attention / Disconnected). FR-4.5 One Velocyverse account/org can connect one or more client tenants (data model supports many-to-one Org → TenantConnection for future MSP/multi-client support, even though multi-client UI is Phase 2). FR-4.6 On successful connection, the dashboard updates to the post-connection state offering Quick and Detailed Assessment (Trial remains available). 8.5 Automated Data Collection Engine (shared by Quick &amp; Detailed) ID Requirement FR-5.1 Data collection is implemented as a configuration-driven pipeline iterating over a MODULES registry (Entra ID, M365 Admin Center, Purview, Email, Intune, Cloud Apps, Teams, SharePoint) — not hard-coded per-module logic — so modules can be added/modified without structural rework. FR-5.2 For each module, the pipeline calls the relevant Microsoft Graph / Graph Security API endpoints, using only the previously consented scopes. FR-5.3 Quick Assessment executes only the 'critical control' subset of API calls per module; Detailed Assessment executes the full control set per module. FR-5.4 If a required scope is missing or an API call fails for a module, that module is flagged 'Permission Not Granted' / 'Collection Failed', the assessment continues for remaining modules (partial assessment is allowed and clearly labeled), and dependent controls are marked 'Not Applicable' rather than 'Failed'. FR-5.5 Raw collected data is persisted (object storage) per assessment/module for traceability, audit, and potential re-scoring without re-collection. FR-5.6 A loading/progress screen shows stage-by-stage status (Initializing → Collecting Data → Analyzing Data → Preparing Results) with percentage complete, matching the existing wireframe. FR-5.7 Data collection must be idempotent and safely retryable (network/API failures should not corrupt partial state). FR-5.8 Rate limiting / throttling handling for Microsoft Graph (respect 429 Retry-After) is required given the volume of calls per assessment. 8.6 Data Validation &amp; Normalization ID Requirement FR-6.1 Raw Graph API responses are validated against expected schemas per module before being handed to the Assessment Engine. FR-6.2 Data is normalized into a consistent internal representation (e.g., unify differing Graph API versions/response shapes, normalize timestamps, dedupe overlapping signals collected from multiple endpoints). FR-6.3 Validation failures for a specific data point should degrade gracefully (mark the specific control as 'Unable to Verify') rather than failing the entire module/assessment. 8.7 Assessment Engine ID Requirement FR-7.1 The Assessment Engine evaluates normalized data against the Control Catalog (Section 15), producing a Pass / Fail / Not Applicable / Needs Manual Review result per control, with supporting evidence captured. FR-7.2 The Control Catalog is externalized (database-driven, versioned) — not hard-coded in application logic — so controls can be added, updated, or re-weighted without a code deployment. FR-7.3 Each control maps to one or more industry framework references (e.g., CIS Microsoft 365 Foundations Benchmark, Microsoft Secure Score actions) for credibility and future compliance-mapping features. FR-7.4 Controls tagged 'automatable: false' (or that return an ambiguous automated result) are routed to the Manual Assessment Workflow for Detailed Assessments; for Quick Assessments these controls are simply excluded from scoring/marked Not Applicable, since Quick has no manual step. 8.8 Scoring &amp; Recommendation Engine ID Requirement FR-8.1 Each control carries a weight and severity; per-module score = weighted pass rate of applicable controls in that module (0–100). FR-8.2 Overall score is a weighted roll-up of module scores (weighting scheme to be defined/tunable, not hard-coded). FR-8.3 Score bands (e.g., Poor / Fair / Good / Excellent) and their thresholds are configurable, not hard-coded, to allow tuning post-launch. FR-8.4 For every Failed control, the engine generates a human-readable recommendation (remediation guidance); recommendations are ranked by severity for the 'Top Findings' / 'Key Recommendations' views. FR-8.5 For Detailed Assessments, the engine merges automated findings with Assessor-submitted manual findings into a single unified result set before final scoring — the client should not need to know which findings were automated vs. manual unless they drill into detail (source field retained internally for audit/traceability). 8.9 Results Dashboard ID Requirement FR-9.1 Shows: assessment metadata (type, tenant, completion date/time, duration, controls assessed count), overall score gauge with qualitative band, per-module score cards (Entra, Email, Purview, Intune, Cloud Apps, Teams, SharePoint — as many as were assessed), a Results Overview donut (Passed/Failed/Not Applicable), Top Findings (ranked by severity with counts), Next Steps, and Report download (PDF/Excel), matching the existing wireframe. FR-9.2 'View all findings' opens a full, filterable/sortable control-level results table (pass/fail, severity, module, description, recommendation). FR-9.3 Reports/results are retained and viewable for a defined retention window (30 days per existing wireframe copy — confirm as product policy, not just UI copy) after which they may be archived or require re-generation. FR-9.4 'Share Report' allows generating a shareable link or sending the report to another recipient (define access control: expiring link vs. requires login — flagged as an open question, Section 17). 8.10 Assessment History ID Requirement FR-10.1 Users see a table of all past/ongoing assessments: Request ID, Type, Client/Tenant Name, Requested On, Completed On, Status (Completed/In Progress), Overall Score, and an action to View Report or Continue (for in-progress Detailed Assessments). FR-10.2 Supports search (by request ID or name) and filtering by type/status. 9. Manual Assessment Workflow (Detailed Tier) This is the differentiator of the Detailed Assessment and the most operationally complex part of the system — it is effectively a lightweight case-management workflow layered on top of the automated pipeline. 9.1 Trigger When a Detailed Assessment's automated pass completes, the Assessment Engine determines whether any evaluated controls are tagged non-automatable or returned a 'Needs Manual Review' result. If so, the assessment status is set to Pending Manual Review and a request record is created in the Admin queue with status Unassigned. 9.2 Requirements ID Requirement FR-11.1 Every Detailed Assessment requiring manual review must appear in the Admin's Active Detailed Requests queue with client name, request date, and status. FR-11.2 Admin can assign a request to any Active Assessor; reassignment must be supported (e.g., Assessor unavailable). FR-11.3 Once assigned, the request appears in that Assessor's Assigned Assessment Requests list; it disappears from other Assessors' views. FR-11.4 The Assessor's workspace for a request shows: (a) the automated findings already collected, organized by module/control, (b) a way to record a manual finding for each non-automatable control (result + evidence + notes), (c) a way to request supporting documents/business context from the client, (d) a way to mark the review complete. FR-11.5 Requesting supporting documents from the client triggers a client-facing notification and a document upload / questionnaire response surface; this can loop (Assessor may request follow-up documents) until the Assessor has enough information. FR-11.6 Client-submitted documents/answers are only visible to the assigned Assessor and Admins, not to other Assessors. FR-11.7 On submission, manual findings are fed into the Scoring &amp; Recommendation Engine, merged with the automated result set, and the assessment status moves to Completed; the client is notified and the final Results Dashboard/report becomes available. FR-11.8 Full audit trail: every status transition (Unassigned → Assigned → In Review → Awaiting Client → Completed) is timestamped and attributable to a user. 9.3 Status Model Status Meaning Who can transition it Unassigned Automated pass complete; awaiting Admin assignment System (entry) → Admin (exit) Assigned Assessor identified, work not yet started Admin In Review Assessor actively working the request Assessor Awaiting Client Assessor requested docs/info, waiting on client Assessor / Client action Completed Manual findings submitted, merged, report available Assessor (submits) → System (finalizes) 10. Admin Portal Requirements ID Requirement FR-12.1 Admin Dashboard summarizes: Active Detailed Requests count, Assessors count, and quick links (View Requests, Manage Assessors, Change Password), matching the existing wireframe. FR-12.2 Active Detailed Requests view: list/manage all Detailed Assessment requests needing assignment or in progress, with the ability to assign/reassign an Assessor. FR-12.3 Assessors view: table of all Assessors (Name, Email, Phone, Status, Added On) with actions to Add, Rename, Change Email/Phone, Remove. FR-12.4 Released Reports view: audit list of completed/released Detailed Assessment reports. FR-12.5 Admin actions (assign, remove Assessor, etc.) are all audit-logged. FR-12.6 (Phase 2 candidate, flag not build) Admin-level analytics: conversion funnel, assessment volume, average Assessor turnaround. 11. Assessor Portal Requirements ID Requirement FR-13.1 Assessor Dashboard shows Assigned Assessment Requests and Completed Assessment Requests as primary navigation, matching the existing wireframe. FR-13.2 Assigned Assessment Requests list shows request ID, client name, assigned date, and due/SLA indicator if defined. FR-13.3 Assessor Assessment Page (the core workspace) implements the workflow in Section 9.2 (FR-11.4). FR-13.4 Completed Assessment Requests is a read-only historical list for the Assessor's own past work. FR-13.5 Assessors have the same account-management surface as Clients (Change Password, Change Name, Phone Number, Email, Delete Account) minus billing/org-level settings. 12. Non-Functional Requirements 13.1 Security This is a security-assessment product; the platform's own security posture is existential to credibility. Follow OWASP ASVS practices minimum; plan for a third-party penetration test before GA. All Microsoft Graph permissions requested must be read-only / least-privilege — never request write/modify scopes. Access tokens/refresh tokens for connected tenants must be encrypted at rest (e.g., envelope encryption, secrets manager / Azure Key Vault) — never stored in plaintext. Role-based access control enforced at the API layer (not just UI) for Client/Admin/Assessor boundaries — an Assessor must be structurally unable to query another Assessor's assigned requests, not just UI-hidden from them. All authentication supports MFA; enforce strong password policy; rate-limit login attempts. Full audit logging of: consent grants/revocations, data collection runs, admin actions, assessor actions, report access/downloads. 13.2 Privacy &amp; Compliance Collected M365 configuration data is customer data — handle under a clear Data Processing Agreement; the existing sign-up screen already references 'data transfer, hosting and processing outside the EU' — data residency commitments must be decided and reflected accurately in ToS/Privacy Policy (do not just leave placeholder copy). Support data deletion on request (GDPR-style right to erasure) including cascading deletion of raw collected data in object storage. Target compliance posture appropriate for a B2B security SaaS handling sensitive tenant configuration data: SOC 2 Type II readiness should be a design consideration from day one even if certification comes later. 13.3 Performance &amp; Scalability Quick Assessment: full pipeline (collection → validation → scoring) should complete in well under 10 minutes for a typical tenant. Data collection must be horizontally scalable (queue/worker model) to support many concurrent assessments without one large tenant blocking others. Microsoft Graph throttling must be handled gracefully (backoff/retry) without failing the whole assessment. 13.4 Availability &amp; Reliability Target 99.5%+ uptime for the client-facing app once GA. Assessment runs must be resumable/retryable on transient failure rather than forcing a full restart. 13.5 Multi-Tenancy (platform architecture, not M365 tenancy) The platform itself is multi-tenant SaaS (many Velocyverse customer Orgs); strict data isolation between Orgs is required at the database and storage layer. 13.6 Auditability Every score must be explainable — the platform should always be able to answer 'why did we fail this control' by pointing to the exact evidence collected, for defensibility in compliance/audit contexts. 14. Permission &amp; Incremental Consent Strategy Direct answer to the concern raised: no, the platform should not — and technically does not need to — request every Microsoft Graph permission in one blanket consent screen. A single request listing 15–20 high-privilege 'Read.All' scopes is exactly the kind of prompt that makes a Global Admin hesitate or bail out entirely, and it also violates least-privilege best practice. The fix is to request only what the specific action the user just took actually needs, at the moment they take it. 24.1 Core Principle: Consent Scope Is Derived From (Assessment Tier + Modules), Not Requested Upfront This formalizes and extends the per-module consent pattern already implied by the original flow diagram (each module showing its own 'Users Grants the Required Permissions' step) into an explicit, tier-aware algorithm: Trial Assessment requests zero Graph permissions — it needs none (Section 21.1). The first time a user runs a Quick Assessment, the system resolves the minimum scope set needed for Quick's critical-control subset across whichever modules Quick covers, and requests only those — not Detailed's deeper scopes. If that same user later runs a Detailed Assessment, the system diffs the full Detailed scope requirement against what's already been consented (from the earlier Quick run) and requests only the incremental delta — the user is never re-prompted for scopes they already granted. Within either tier, scopes are still requested grouped by module (Entra, Email, Purview, etc.) with a short plain-English description of exactly what that module's access enables, matching the original wireframe's per-module structure — this keeps each individual consent screen short and understandable rather than one long wall of permissions. If the admin declines a specific module's scopes, that module is marked 'Permission Not Granted' and the assessment proceeds without it (already specified in FR-4.3 / Diagram 2) — consent is granular and non-blocking per module. Incremental, tier-aware consent resolution — requests only the delta scope needed for the action just taken 24.2 Technical Mechanism (Microsoft identity platform) Microsoft's OAuth2/OIDC admin-consent flow natively supports incremental consent: a scope parameter can be submitted to the /adminconsent (or /authorize with prompt=consent for admin-restricted scopes) endpoint containing only the specific permissions needed for that step. Previously granted scopes remain granted — Azure AD accumulates consent on the tenant's service principal for that app registration rather than replacing it. The system of record for 'what has this tenant actually granted us' is TenantConnection.consented_scopes (Section 15.1) — always diff against this stored value, not against what the UI last showed, since the admin could have modified consent directly in their own Entra admin center. Detect revocation: if a previously consented scope starts failing with an authorization error on a Graph call, treat that specifically (not as a generic API failure) — update TenantConnection status and prompt reconnection for just that module, per FR-4.4. Because these are org-wide, privileged 'Application' permissions (not delegated 'Sign in and read user profile' style scopes), each incremental grant still requires a Global Admin (or equivalent privileged role) to approve — this is expected and appropriate for this class of access; the goal of incremental consent here is to minimize the size and frequency of each ask, not to avoid admin approval altogether. 24.3 Practical Sequencing (recommended default) Step When it happens What's requested 1 User runs Trial Nothing 2 User clicks 'Connect Your Tenant' intending to run Quick Critical-subset scopes for the modules Quick covers, requested as one consent screen per module (or grouped, if Microsoft's consent UI allows a single combined screen with clear per-resource breakdown — implementation detail to validate) 3 Same user later upgrades to Detailed Assessment for the first time Only the incremental additional scopes Detailed needs beyond what Quick already has — typically a smaller ask than step 2 4 A future product update adds a new module or a new control requiring a new scope Only that new scope, requested the next time the user runs an assessment that would use it — never a forced mass re-consent 24.4 UX Recommendation Before each consent redirect, show an in-app screen (not just Microsoft's native consent screen) that plainly states, in the user's language rather than Graph scope names: what module is being connected, what specific data will be read (e.g., 'MFA enrollment status and Conditional Access policy configuration'), and confirms it is read-only. This matches the existing wireframe's 'Secure and read-only connection' messaging and should be applied consistently at every incremental step, not just the first one. 25. Product Enhancement Recommendations (Beyond Confirmed Scope) Direct answer to 'what else would make this a complete, powerful, efficient tool' — these are not required for the first build, but are flagged because several of them reuse infrastructure already in this PRD almost for free, and materially increase both product value and monetization surface (Section 23). Ordered roughly by leverage (value relative to build cost given what's already planned). 25.1 High Leverage (reuses existing infrastructure directly) Idea Why it's high leverage Continuous monitoring &amp; drift alerts The Graph connector, Control Catalog, and Assessment Engine already exist — this is mostly 'run the existing pipeline on a schedule/webhook and diff against the last result' plus a notification. Also a strong subscription upsell (Section 23.2). Score trend / history dashboard Assessment and Finding records already carry timestamps and scores — a trend chart is largely a query/visualization feature on data already being captured, not new data collection. AI-generated executive summary narrative The report's 'Executive Summary' section (Section 12.1) already needs plain-English positives/negatives per area — an LLM can draft this from structured Finding data, reducing manual report-writing effort (relevant for Assessor efficiency in Detailed Assessments, Section 23.2 margin improvement). Assessor-assist suggestions For the manual review workflow (Section 9), surface AI-suggested findings/recommendations for non-automatable controls based on the automated data already collected, which the Assessor reviews and confirms rather than writing from scratch — cuts Assessor time per request, directly improving the target in Section 3.2 (&lt; 90 minutes). Compliance framework selector in the report UI Control Catalog already carries framework_refs (Section 15.1) — exposing a toggle to view the same underlying Findings mapped to a different framework's language is largely a presentation-layer feature once that field is populated. 25.2 Medium Leverage (moderate new build, clear value) Integrations: push findings to Jira/ServiceNow/Slack/Teams so remediation work is tracked where the customer's team already works, rather than only living inside Velocyverse. MSP multi-client dashboard: an aggregate, at-a-glance risk view across all tenants an MSP manages (average score, worst-performing tenant, overdue re-assessments) — already implied by the data model's Org → many TenantConnections shape. Notification/alerting engine: beyond drift alerts, notify on assessment completion, Detailed Assessment status changes, consent revocation, and plan/credit exhaustion — reduces the need for customers to keep checking back manually. Public API for programmatic assessment triggering — lets sophisticated customers wire an assessment into their own CI/CD or change-management process (e.g., 'run a Quick Assessment automatically after any Conditional Access policy change'). 25.3 Lower Near-Term Priority (credible, but needs scale or partnerships first) Peer/industry benchmarking ('compare your score to similar-sized companies') — needs real assessment volume and a carefully designed anonymization/consent model before it's meaningful or safe to ship. One-click auto-remediation (having the platform actually change a tenant's configuration, not just report on it) — powerful but requires write-scope Graph permissions, a much higher trust bar, and a very deliberate safety/rollback design; recommend treating as a distinct, carefully-scoped future initiative rather than folding into the assessment product's permission model. Certification badge program and cyber-insurance partnerships (Section 23.2) — valuable but primarily gated by business development and legal work, not engineering. 25.4 Recommendation Do not build any of Section 25 in the first release — the recommended build sequence in Section 5.3 and 19 is already substantial. This section exists so Kilo AI's architecture (module-driven Control Catalog, isolated Graph Connector Service, ledger-based usage tracking, source-tagged Findings) is built in a way that doesn't have to be re-architected to add these later. Several of the data model choices already made in Section 15 and 22.5 (e.g., Finding.source, ControlCatalog.framework_refs, UsageLedger) exist specifically because they're cheap to include now and expensive to retrofit. 26.
